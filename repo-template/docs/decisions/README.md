# Architecture Decisions

本目录记录当前项目的重要技术决策。目标是保存“为什么这么做”，避免未来重复讨论或误改。

## 什么时候新增 ADR

当决策会长期影响以下内容时，新增 ADR：

- 架构边界、模块依赖、公共 API 或数据模型。
- 框架、数据库、缓存、队列、部署方式、认证/权限模型。
- 性能、安全、可靠性、可观测性或维护成本。
- 明确接受某个长期限制、风险或技术债。
- 某个方向未来很可能被再次质疑。

## 什么时候不要新增 ADR

- 一次性 bug fix。
- 普通实现细节。
- 不改变长期边界的小重构。
- 已经不再相关的临时调查过程。

## 命名

使用递增编号和简短英文标题：

```text
0001-use-postgres-for-primary-storage.md
0002-keep-auth-in-edge-middleware.md
```

## 状态

- Proposed：提议中
- Accepted：已接受
- Superseded：已被替代
- Deprecated：不再推荐，但历史上仍存在

## 维护规则

- ADR 应短而清楚，优先记录背景、决策、影响。
- 如果决策被替代，不要删除旧 ADR；将状态改为 Superseded，并链接新 ADR。
- 不记录一次性过程细节。
