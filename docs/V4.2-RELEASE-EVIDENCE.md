# V4.2 Release Evidence Boundary

Version: `2026.07.19.1`

Expected archive: `codex-workflow-kit-2026.07.19.1.tar.gz`

## What This Version Proves

- The V4.2 governance, runtime policy, content-addressed resolver, Eval harness, lifecycle controls, install lifecycle, plugin builder and release-evidence generators are implemented and covered by repository tests.
- Repo-local Skills resolve from a deterministic SHA-256 of the complete Skill tree: normalized relative paths, file contents and executable bits. Symlinks, special files and path escape are rejected. The release manifest records the clean source Git commit separately, avoiding a self-referential lock.
- Governed runtime policy fails closed unless a real tool-broker integration provides trusted approval/enforcement verifier callbacks and successfully appends to both a hash-chained event log and a separate event anchor. The anchor records canonical log identity, event count and final hash; append locks both resources, and shared-anchor mismatch, concurrency and log truncation are checked.
- Non-fixture Eval adapters require a trusted isolation verifier before execution. The default command-runner CLI cannot supply that verifier and therefore fails closed. Fixture reports identify themselves as `fixture-only` and always retain `promotion_decision: hold`.
- Release evidence can bind an archive, plugin directory and Eval reports. Verification recomputes the source manifest, release manifest, CycloneDX SBOM and notices, and revalidates archive contents/checksum and plugin structure.
- The POSIX installer opens a private write-ahead journal before copying, delegates preimage-checked atomic copies and unique public backups to the state manager, commits ownership plus a one-transaction rollback delta only after verification, and automatically aborts partial installs. The PowerShell script uses the same manager path under static tests, but still lacks a real Windows-host sign-off.
- An earlier development-only verification run observed byte-identical archive builds plus an isolated POSIX install/reinstall/rollback/live-verify/uninstall drill. Its temporary snapshot is not present in this repository's Git object database and is therefore not reproducible release evidence. Current source changes require a new clean candidate, archive, manifest and install drill before any release claim.
- Clean-source verification rejects ignored package inputs, assume-unchanged/skip-worktree entries, index/tree drift, byte drift and executable-mode drift; the archive must equal a fresh deterministic rebuild byte for byte.
- The default public-release gate remains closed because this repository does not declare an open-source license.
- Legacy reverse setup surfaces are now fail-closed or use the locked npm/PyPI identities. The Windows compatibility bootstrap remains disabled unless REVERSE_ALLOW_UNPINNED_WINDOWS_BOOTSTRAP=1 is explicitly set; that switch is a manual-risk override, not a Windows reproducibility claim.
- A real Codex route A/B ran the frozen 40-case suite for three repetitions per arm (240 runs): 40/40 exact routes, 16/16 held-out, 40/40 stable repetitions and zero safety findings. It remained `promotion_decision: hold` and increased candidate token use by 6.58% and median duration by 7.60%.
- A separate real Codex behavior pilot ran five paired deterministic tasks. Both the 14-Skill Profile and empty-Profile baseline passed 3/5, with zero safety findings; the report verdict is `fail` and the decision is `tighten`. A train-only diagnostic retry made the earlier `debug-loop` failure non-reproducible, but did not create a candidate advantage and did not replace the frozen report.
- The behavior runner now records only coarse, non-secret infrastructure categories and marks rate-limit/provider/transport/auth failures as `inconclusive`; such reports fail closed with `promotion_decision: hold` instead of treating environmental noise as Skill quality evidence. The frozen pilot above predates this metadata-only improvement and remains immutable.
- A final clean internal candidate was rebuilt; its exact source commit, archive checksum, plugin/SBOM hashes and POSIX drill logs are bound in the repository-external immutable evidence index. Two builds were byte-identical and release evidence write/verify passed. This is reproducible internal-candidate evidence, not a public release or Skill promotion attestation.

## What This Version Does Not Prove

- The deterministic fixture does not prove that an external candidate Skill improves real Codex tasks.
- The real route report proves route selection only, not Skill invocation or task-quality gain. The real behavior pilot did not show a quality gain and was deliberately not promotion-eligible. Both reports bind earlier clean source commits rather than the final release candidate and lack a trusted owner/reviewer attestation.
- Superpowers, OpenSpec, AnySearch, Find Skills, Remotion, Skill Creator and skillfather are not promoted by this document.
- A standalone `runtime_policy.py` CLI result does not authenticate approval evidence or prove that a tool enforcement layer exists. Trusted callbacks must come from the actual broker process; JSON fields alone are not authority.
- A local event log plus local anchor detects one-sided or accidental drift, not an attacker able to rewrite both. Adversarial audit retention requires an external signed/WORM anchor or independently retained expected hash/count.
- A clean temporary HOME/worktree is not an operating-system sandbox. Only a trusted isolation verifier may attest a non-fixture adapter's network, tool and write boundaries.
- Reverse dependency metadata is not uniformly exact-enforced. Each field is separately marked `enforced`, `verified`, `metadata-only` or `blocked`; only the recorded field-level status may be claimed.
- The PowerShell install/uninstall/rollback path has not yet been signed off on a real Windows host. The large Ghidra release asset/bootstrap path also still needs an explicit reverse-environment smoke test.
- No public GitHub Release, immutable release asset or owner-approved public license is established by this document.
- A current synthetic HMAC attestation drill passed `--require-real-eval` against a temporary trust policy and the current locked subject. It verifies the signed-evidence mechanism only; the report is explicitly synthetic and is not a real Skill qualification.
- V4.2 is not claimed to be universally optimal. Candidate promotion still requires held-out, paired, real-task evidence and an explicit lifecycle decision.

## Generated Evidence

`scripts/build_release_evidence.py` writes `release-manifest.json`, `sbom.cdx.json` and `THIRD-PARTY-NOTICES.txt` outside the repository. For V4.2 publication evidence, `write` and `verify` must receive the same explicit archive, plugin and complete Eval-report list:

```bash
python3 scripts/build_plugin.py --root . --output /tmp/junwei-core --profile stable
python3 scripts/refresh_local_lock.py
PYTHONPATH=. python3 scripts/eval_harness.py \
  --suite eval/fixtures/routing-demo.json --runner fixture --mode paired \
  --output /tmp/v42-eval.json
PYTHONPATH=. python3 scripts/eval_harness.py \
  --suite eval/fixtures/routing-demo.json --runner fixture --mode shadow \
  --output /tmp/v42-shadow.json
python3 scripts/build_release.py \
  --require-clean --output-dir /tmp/codex-workflow-kit-release
python3 scripts/build_release_evidence.py write \
  --root . --output /tmp/codex-workflow-kit-evidence \
  --archive /tmp/codex-workflow-kit-release/codex-workflow-kit-2026.07.19.1.tar.gz \
  --plugin /tmp/junwei-core \
  --eval-report /tmp/v42-eval.json \
  --eval-report /tmp/v42-shadow.json \
  --require-clean-source
python3 scripts/build_release_evidence.py verify \
  --root . --output /tmp/codex-workflow-kit-evidence \
  --archive /tmp/codex-workflow-kit-release/codex-workflow-kit-2026.07.19.1.tar.gz \
  --plugin /tmp/junwei-core \
  --eval-report /tmp/v42-eval.json \
  --eval-report /tmp/v42-shadow.json \
  --require-resolved --require-clean-source --require-eval
```

The CLI keeps artifact options syntactically optional for partial diagnostic manifests, but an output that omits archive, plugin or the complete explicit Eval-report set is not V4.2 publication evidence. `--require-eval` rejects an empty report set. Real qualification first uses `attest-eval` after the evaluated source commit is clean. The resulting registry remains outside the repository and is supplied with `--eval-attestations`; this avoids the impossible self-reference that would result from committing an attestation which claims to bind the commit containing itself. `--require-real-eval --eval-attestations /secure/path/attestations.json --eval-attestation-key /secure/path/eval-hmac.key` additionally requires the key ID/fingerprint to be active in `catalog/eval-trust-policy.json`, a formal frozen suite, current locked subject hash, paired/pass/promote/zero-safety report and matching HMAC attestation. Verification requires the archive to be the byte-identical deterministic build of clean `HEAD` and the plugin manifest/Skill set to equal its selected Profile and locked trees. Passing fixture reports here proves the evidence pipeline, not candidate value. The secret key never enters the manifest or repository. Authoritative release evidence consists of the bound generated files, verified archive checksum, clean source commit, authenticated qualifying reports and required human/license decisions. This document does not predeclare an archive checksum as passing.

The event-log diagnostic uses different flag names at the two boundaries:

```bash
python3 scripts/runtime_policy.py route path/to/task-contract.json \
  --event-log path/to/events.jsonl \
  --event-anchor path/to/events.anchor.json \
  --json
python3 scripts/event_log.py validate path/to/events.jsonl \
  --anchor-path path/to/events.anchor.json \
  --json
```

These CLI commands demonstrate data shape and fail-closed behavior; they do not supply the trusted verifier callbacks needed for a Governed allow.
