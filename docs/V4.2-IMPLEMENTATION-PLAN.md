# Codex Workflow Kit V4.2 最终实施方案

> 状态：Implementation candidate；真实任务晋升证据与正式发布签署待完成  
> 基线版本：`2026.06.22.1`  
> 基线提交：`e76318c0e747ca9e3b6e5399499ab20a374056fc`  
> 方案日期：2026-07-12  
> 适用范围：本仓库从 V3.2 向 V4.2 的渐进迁移

## 1. 结论

V4.2 采用 **Evidence-Driven Personal Workflow**：

```text
治理面
catalog
  -> resolver
  -> lock
  -> eval report
  -> release manifest
  -> rollback / retire

运行面
薄 AGENTS
  -> Policy Router
  -> 分级 Task Contract
  -> 当前 transition 的唯一 Driver
  -> Overlay / Guardrail
  -> Deterministic Checks
  -> Verifier Policy
  -> 下一状态
```

本次升级的目标不是把 14 个 Skill 扩充为更多 Skill，而是：

- 减少默认上下文和默认安装面。
- 把流程控制权限定到单次状态转换。
- 把任务描述与真实权限强制分离。
- 让外部能力经过可复现的审计、Shadow、Pilot 和 A/B Eval 后再晋升。
- 用真实任务成功率、安全性和人工纠偏量决定保留、合并或退役。

V4.2 是实施基线，不是对“普遍最优”的宣称。完成 P0-P3 后取得的真实运行证据，才决定后续 Skill 是否进入 Stable。

## 2. 当前基线与主要问题

V3.2 已经具备可迁移安装、repo context pack、14 个个人 Skill、外部组件准入、Subagent 协议、逆向能力包和多层验证脚本。这些能力继续保留为迁移基础，但当前存在以下优先问题：

1. `global/AGENTS.md` 同时承担个人原则、路由、Skill 说明、Subagent 合约、MCP/memory、逆向路由和安全规则，持续规则与按需细节混在同一个启动上下文中。
2. 全局安全规则要求外部写入和高风险操作先确认，但逆向章节又包含“必须产生实际副作用”和“授权已预先确认”，形成真实授权冲突。
3. 当前路由主要使用 XS/S/M/L/XL 规模判断；文件数量和任务规模不能可靠表示权限、不可逆性或外部副作用。
4. `Task/Handoff Envelope` 目前主要依赖提示词遵守，尚未清楚区分可强制策略、建议策略和平台无法强制的策略。
5. 现有 Skill 验证偏静态结构与关键词覆盖，不能单独证明 Codex 在真实上下文中正确触发并改善结果。
6. Pilot 状态没有完整映射到安装、隐式调用和 kill switch；“已打包”仍可能被误解为“默认启用”。
7. 外部组件来源、解析版本、评测证据和发布内容缺少四层独立的机器可读事实。
8. reverse pack、运行工具和主工作流发布耦合较强，默认安装面和供应链风险高于日常任务需要。
9. 历史 release 归档继续进入 Git tree 会扩大仓库；停止提交新归档不会自动缩小既有 Git 历史。

迁移必须保持 V3.1 已验证的术语边界：

- `promote != install`
- `pilot != enable`
- `core != runtime/background`
- `approved docs/script != approved external write`

## 3. 不可破坏的架构约束

### 3.1 单一状态转换 Driver

一个任务可以先后经过多个 Driver，但**同一个状态转换只能有一个权威 Driver**。

- Driver 可以推进状态。
- Overlay 提供领域方法，但不能推进或改写状态。
- Guardrail 可以阻止状态推进，但不能自行宣布任务完成。
- Verifier 可以把 `implemented` 推进到 `verified`，或退回 `rework_required`，不能兼任本轮实现者。
- Driver 的权限在对应 transition 完成、失败或取消后立即失效。

禁止同时让 OpenSpec、Superpowers 和自定义总控 Skill 竞争实现阶段。

### 3.2 Contract 与 Enforcement 分离

`Task Contract` 只描述任务意图、范围、验收、审批和可接受副作用，不凭空授予任何权限。

```text
Task Contract
  描述目标、状态、边界、审批和验收

Policy Enforcement
  根据平台能力真正限制工具、路径、网络、凭据和外部目标
```

每条策略必须声明执行等级：

| 等级 | 含义 | Governed 处理 |
| --- | --- | --- |
| `enforced` | 由工具配置、沙箱、allowlist 或包装脚本强制 | 可继续 |
| `verified` | 执行前后可通过确定性检查确认 | 记录证据后继续 |
| `advisory` | 只能依赖指令和人工 review | 涉及关键边界时不得静默继续 |
| `unavailable` | 当前平台无法表达或检查 | 默认 fail closed，并请求明确决策 |

不得把 prompt 中的“禁止”描述成已实现的权限隔离。

Governed allow 的运行时成立条件还包括：

- 真实 tool broker 通过可信 `approval_verifier` 校验审批来源、范围和目标（该动作需要审批时）。
- 真实 tool broker 通过可信 `enforcement_verifier` 证明相应工具、路径、网络或目标限制已安装并生效。
- 审计事件成功追加到 hash-chained event log，并同步更新位于独立路径的 event anchor。

`runtime_policy.py` CLI 仅用于诊断决策和失败路径；它不能自行认证 JSON 审批或宿主强制器，因此不会产生可信 Governed allow。生产集成必须调用 Python API 并注入 verifier 回调，不能通过构造 standalone JSON 绕过宿主信任边界。

### 3.3 单调升级

任务通道在执行中只能从 `Fast -> Standard -> Governed` 自动升级，不能自动降级。

- 用户可以显式选择更高通道。
- 范围扩大、出现外部副作用、判定器失效或触及安全边界时必须重新路由。
- 降级必须作为新决策记录，不能由当前 Driver 为节省流程自行执行。
- “通道不自动降级”不限制 Stable Skill 在严重回归时自动回滚到 last-known-good 版本。

### 3.4 确定性优先，独立验证按证据触发

编译、测试、lint、schema、hash、可复现渲染和明确截图断言优先于主观自评。以下任一条件成立时，使用新上下文 Verifier：

- 通道为 Governed。
- 没有可靠的确定性判定器。
- 结果高度主观，例如视觉设计、内容质量或交互体验。
- 触及安全、认证、权限、数据、公开 API 或兼容性边界。
- 实现上下文过长，存在明显 goal/context drift 风险。
- 测试结果与验收目标之间仍需语义判断。

Verifier 默认只读，接收 Task Contract、最终 diff、验证产物和必要项目事实，不接收完整实现对话。

### 3.5 实验能力与默认运行环境物理隔离

- Lab/Pilot 不安装到默认全局 Skill 路径。
- `allow_implicit_invocation: false` 是附加保护，不替代物理隔离。
- 默认环境只包含通过 Stable 门禁且确实需要隐式发现的能力。
- 6-8 个隐式 Skill 仅作为起始启发式；最终以描述预算、触发准确率和实际收益为准。
- 默认 Skill 描述预算目标不超过平台可用预算的 50%，为项目级 Skill 和未来平台变化留余量。

## 4. 治理面设计

### 4.1 四类事实与一个解析步骤

| 产物 | 回答的问题 | 是否人工编辑 | 是否可作为发布依据 |
| --- | --- | --- | --- |
| `catalog/components.yaml` | 想要什么 | 是 | 否 |
| Resolver | 如何把期望状态解析为确定版本 | 代码 | 否 |
| `catalog/upstreams.lock.json` | 实际解析到了什么 | 仅由 Resolver 更新 | 否 |
| `evals/reports/<run-id>.json` | 证据证明了什么 | 机器生成，人工签署结论 | 作为门禁输入 |
| `release-manifests/<version>.json` | 最终发布了什么 | 构建生成 | 是 |

`catalog` 是期望状态的单一事实源；`lock` 是解析结果，不与 catalog 竞争所有权。发布只读取锁定版本和通过门禁的 Eval，不直接解析浮动引用。

### 4.2 Catalog 最小字段

每个组件至少记录：

```yaml
id: superpowers
kind: skill-plugin
role: driver
transitions:
  - approved_spec_to_planned
  - planned_to_implemented
profiles:
  - standard
source:
  url: https://github.com/obra/superpowers
  ref_policy: exact-commit
license: MIT
status: repo-pilot
implicit: false
risk:
  network: false
  workspace_write: true
  external_write: false
compatibility: []
eval_suite: superpowers-driver-v1
kill_switch: true
retire_when: []
```

现有 Skill frontmatter 中的 `risk`、`source_repo`、`source_type`、`status`、`auth`、`network` 和 `write_surface` 等治理字段迁移到 catalog；Skill frontmatter 保留 Agent Skills 标准字段，必要的可移植扩展放入 `metadata`。

### 4.3 Lock 最小字段

每个外部组件锁定：

- 来源 URL。
- 精确 tag（若有）和完整 commit SHA。
- 获取内容的 SHA-256 或等价内容哈希。
- 解析时间和 Resolver 版本。
- License 结论与 notice 路径。
- Codex、运行时和项目依赖兼容范围。
- 允许的网络域名和所需权限。
- 最近通过的 Eval suite、模型、harness 版本和报告 ID。
- last-known-good 锁定项。

禁止在 Stable 解析中使用 `main`、`master`、`HEAD`、`@latest`、可移动 tag 或 Docker `:latest`。

repo-local Skill 使用 `content.scope: skill-tree`：确定性 SHA-256 覆盖整个 Skill 目录的规范化相对路径、文件内容和可执行位，而不是只覆盖 `SKILL.md`。解析、governance 校验和 plugin staging 都复用同一算法；符号链接、特殊文件、路径逃逸或复制后 hash 不一致一律 fail closed。

reverse 可选依赖不能用一个笼统的“已精确锁定”结论描述。`catalog/reverse-dependencies.lock.yaml` 对 package/version/integrity、repository/commit、asset/url/sha256 等字段分别记录：

- `enforced`：bootstrap 直接按该值执行并拒绝漂移。
- `verified`：执行前后通过确定性检查核验。
- `metadata-only`：只记录盘点证据，不宣称运行时强制。
- `blocked`：缺少可信 digest/来源时禁止安装。

发布和 bootstrap 只能按字段声明的实际强度作出结论；npm SRI、PyPI SHA 或 release tag 出现在 lock 中，不自动等于安装器已验证它。

### 4.4 Release Manifest

Release manifest 至少包含：

- toolkit 版本和源码 commit。
- catalog 与 lock 的内容哈希。
- 实际包含的插件、Skill、脚本、模板和可选包。
- 每个外部组件的完整 SHA、License 和内容哈希。
- 关联 Eval report ID。
- 目标平台和兼容范围。
- archive checksum、构建环境摘要和重现命令。
- last-known-good 版本和回滚说明。

发布归档作为 GitHub Release asset 分发；V4.2 生效后不再把新的 tarball 提交到 Git。既有归档和 Git 历史是否清理属于独立、显式批准的维护任务。

发布证据的 `write` 与 `verify` 必须显式绑定同一 archive、plugin 和全部 Eval reports。`verify` 不信任已经生成的 JSON/TXT：它重算源码 `MANIFEST.sha256`、release manifest、CycloneDX SBOM 和 notices，并重新验证归档内容/checksum 与 plugin 结构。fixture Eval 可以绑定为管道 smoke，但仍是 `hold`，不能满足候选晋升门禁。

## 5. 运行面设计

### 5.1 薄 `AGENTS.md`

全局 `AGENTS.md` 只保留：

- 个人长期沟通与工程偏好。
- 不可越过的安全和外部副作用边界。
- Policy Router 的最小路由规则。
- 验证、停止和升级原则。
- 如何按需加载项目规则和 Stable Skill。

以下内容移出全局启动上下文：

- 大段 Skill 功能清单和关键词列表。
- 逆向完整路由、工具 bootstrap 和工具索引细节。
- Subagent 完整 envelope 模板。
- MCP、memory、code graph、hooks 的试点说明。
- 具体项目命令、详细检查表和长模板。

迁移目标不是追求固定字节数，而是删除重复规则，并通过描述预算与触发 Eval 验证精简效果。初始工程目标为内容减少至少 50%，且所有安全边界和用户稳定偏好仍有测试覆盖。

### 5.2 Policy Router

Router 不使用文件数量估算任务大小，而根据风险、可逆性、判定器和外部副作用选择通道。

| 通道 | 必须满足或触发的条件 | Contract 形态 | 默认 Driver |
| --- | --- | --- | --- |
| Fast | 需求明确；工作区内可逆；无外部副作用；有强判定器；不跨安全/公开接口边界 | 内存极简状态，不落文件 | native Codex |
| Standard | 存在设计选择、多模块影响或需要 TDD；仍可在工作区回滚 | 保留在任务上下文 | Superpowers 或明确的 native transition |
| Governed | 生产/外部写入、凭据、权限、数据迁移、公开 API、不可逆操作、正式审批或安全边界 | 持久化审计记录 | 按状态交接 |

补充路由规则：

- 项目内普通依赖变更通常为 Standard，并叠加 dependency guardrail；全局安装、系统级安装或供应链来源不明升级为 Governed。
- 只读公开网络研究不自动等于 Governed，但必须记录来源和输入边界；携带凭据、访问私有系统或向外部服务提交内容时升级。
- 低风险但主观的 UI 任务至少为 Standard，并由 Verifier Policy 决定是否使用新上下文视觉复核。
- 任一 Governed 触发条件优先于其他条件。

### 5.3 分级 Task Contract

Fast 仅在当前任务内维护：

```yaml
lane: fast
write_roots:
  - <workspace-path>
acceptance_checks: []
```

Fast 不创建审计文件，不要求正式 handoff，不为了记录而增加流程税。

Standard 在任务上下文中维护：

```yaml
lane: standard
state: planned
transition: planned_to_implemented
transition_driver: superpowers

intent: ""
write_roots: []
network:
  mode: none
  allowlist: []
credentials: []
external_targets: []
package_install: project-only
production_access: false
destructive_actions: false

required_artifacts: []
acceptance_checks: []
verification_mode: deterministic
escalation_reasons: []
handoff: verify
```

Governed 追加持久化审计字段：

```yaml
contract_id: ""
created_at: ""
repo_revision: ""
request_provenance: ""

approval:
  required: true
  status: pending
  granted_by: null
  granted_at: null
  scope: []

external_effects: []
policy_enforcement: []
evidence_paths: []
rollback_plan: ""
retention: ""
```

批准必须带来源、范围和时间；模型自行写入 `granted` 不构成批准。Governed 记录默认放在目标仓库声明的 evidence root；未声明位置时先请求确认，不静默写入 workspace 外部。

### 5.4 权限维度

权限不能压缩成互斥的 `read | workspace-write | external-write`。至少独立表达：

- `read_roots`
- `write_roots`
- `network.mode` 与 `network.allowlist`
- `external_targets` 及 read/write 方法
- `package_install`：`none | project-only | user | system`
- `credentials`：只允许命名引用，不记录密钥值
- `browser_actions`：`inspect-local | inspect-external | submit-external`
- `production_access`
- `destructive_actions`
- `approval`

任何字段缺失都按最小权限解释，不能按最宽权限补全。

### 5.5 审计日志与独立锚点

Governed allow 必须同时写入 event log 和独立 event anchor；只有日志自身的 hash chain 不足以检测整段尾部被删除。anchor 保存 canonical log identity、事件数量与末尾 hash，验证时三者必须匹配。

- 日志与 anchor 必须使用不同路径。
- append 按稳定顺序同时取得 log 与 anchor 的跨进程排他锁，先验证现有绑定，再追加日志、持久化并原子更新 anchor；两个日志不得共享一个 anchor。
- 锁不可用、并发锁争用、日志/anchor 任一缺失、事件数/hash 不匹配或链损坏都 fail closed。
- CLI 中运行时参数为 `--event-anchor`；独立日志验证参数为 `event_log.py validate ... --anchor-path ...`。
- 这里的“独立”只表示不同路径并可检测单边/意外漂移，不表示独立信任域。能同时改写本地 log 与 anchor 的主体仍可重算二者；需要抗此威胁时，broker 必须把 expected hash/count 发布到外部签名、WORM 或其他可信 anchor store。
- 任何调用者都不能提供 sequence、event ID、previous hash 或 hash 等链字段。

## 6. 任务状态机与 Driver 交接

### 6.1 核心状态

```text
discovered
  -> scoped
  -> approved_spec (Governed / 正式规格)
  -> planned
  -> implemented
  -> verified
  -> released | closed

implemented
  -> rework_required
  -> implemented

scoped | approved_spec | planned | implemented
  -> blocked | cancelled
```

### 6.2 Transition 所有权

| Transition | 权威 Driver | 允许叠加 | 关键出口证据 |
| --- | --- | --- | --- |
| `discovered_to_scoped` | Policy Router / main agent | onboarding、research | lane、范围、风险、判定器 |
| `scoped_to_approved_spec` | OpenSpec **或** `spec-kit-xl` | security、decision-record | 规格、非目标、验收、批准来源 |
| `scoped_to_planned` | Superpowers 或 native（按 lane） | domain overlay | 可执行计划与检查 |
| `approved_spec_to_planned` | Superpowers | domain overlay | 计划映射到已批准验收项 |
| `planned_to_implemented` | Superpowers 或 Fast native | frontend/design、dependency、security guardrail | diff、测试和实现证据 |
| `implemented_to_verified` | deterministic runner 或 independent verifier | frontend QA、security reviewer | PASS/FAIL/NEEDS_CONTEXT 和证据 |
| `implemented_to_rework_required` | independent verifier | guardrails | 失败项与复现路径 |
| `verified_to_released` | 用户批准的 release driver | release-readiness guardrail | release manifest、checksum、rollback |

Guardrail 的 veto 不等于它拥有 transition。任何 Driver 都不能把自己的输出同时作为独立验证结论。

### 6.3 OpenSpec 与 Superpowers

OpenSpec 仅拥有 `scoped -> approved_spec`：

- 产出 proposal、delta spec、design、tasks 或对应 artifact。
- 明确目标、非目标、验收标准、风险、兼容性和批准来源。
- 规格未获外部有效批准时，状态只能是 `spec_ready_for_review`，不能伪造 `approved_spec`。

Superpowers 在收到已批准规格后拥有 `approved_spec -> planned -> implemented`：

- 将每个实施步骤映射到规格验收项。
- 使用其计划、TDD、调试和实现流程。
- 发现规格错误或范围变化时，返回 `spec_revision_required`，不能静默改写规格。

同一任务中：

- OpenSpec 与 `spec-kit-xl` 在规格 transition 上二选一。
- 选择 Superpowers 作为实现 Driver 后，不再调用 OpenSpec `apply` 控制实现。
- OpenSpec 的 artifact consistency 检查可以作为只读 Guardrail，但不能同时充当独立 Verifier。
- OpenSpec 与 `spec-kit-xl` 完成 A/B 前都保持显式 Pilot；胜者晋升，败者进入 Deprecated/Retired。

## 7. Overlay、Guardrail 与 Verifier

### 7.1 角色定义

| 角色 | 可以做什么 | 不可以做什么 |
| --- | --- | --- |
| Driver | 推进当前 transition | 同时自证验证通过 |
| Overlay | 提供前端、视频、依赖等领域方法 | 改变 lane、审批或状态所有权 |
| Guardrail | 检查并阻止不安全推进 | 自行实施或宣布完成 |
| Verifier | 在独立上下文判断验收是否满足 | 默认修改实现或扩大范围 |

### 7.2 Verifier 输出契约

```yaml
verdict: pass | fail | needs_context
contract_id: ""
checks_run: []
evidence: []
failed_acceptance: []
safety_findings: []
scope_drift: []
recommended_transition: verified | rework_required | blocked
```

Verifier 不接受“实现者表示已完成”作为证据。机械条件用脚本断言；主观条件用盲评或独立 reviewer；两类证据有冲突时不得自动通过。

## 8. Skill 与外部组件生命周期

### 8.1 状态

```text
Discovered
  -> Audited
  -> Shadow
  -> Repo Pilot
  -> Stable
  -> Deprecated
  -> Retired

任意未通过状态 -> Rejected
Stable 严重回归 -> Suspended -> Rolled Back | Retired
```

### 8.2 状态门禁

| 状态 | 运行权限 | 安装位置 | 晋升条件 |
| --- | --- | --- | --- |
| Discovered | 无 | 不安装 | 来源和用途清楚 |
| Audited | 只读审计 | staging | License、安全、内容和重叠审计通过 |
| Shadow | 只输出路由建议，不调用工具、不写文件 | Eval 隔离环境 | 路由对比无严重误触发 |
| Repo Pilot | 显式调用；固定 SHA；最小权限 | repo-local 或隔离 HOME | 配对真实任务通过 |
| Stable | 按证据决定显式或隐式 | approved profile | 触发、行为、安全和回滚门禁通过 |
| Deprecated | 禁止隐式；提示替代项 | 仅兼容期 | 迁移窗口结束 |
| Retired | 无 | 从运行路径移除 | 保留锁和历史 Eval |

Shadow 由 Eval Harness 实现，不假定 Codex 原生提供：

- 候选只回答“若启用会如何路由、加载哪些能力、要求哪些权限”。
- 不获得写权限，不调用外部工具，不改变任务结果。
- 将建议与实际 Driver、人工判断和最终结果比较。

Canary 仅对明确项目或任务家族启用候选锁定版本。每个 Stable 组件必须具备：

- kill switch。
- last-known-good 版本。
- 一条经过演练的回滚命令或操作路径。
- 明确的回滚触发条件。
- 明确的 Deprecated/Retired 条件。

安全违规、未授权外部写入、凭据暴露、不可恢复的数据损坏或关键权限绕过一旦出现，立即 kill、停止 Canary 并回滚，不等待统计显著性。

### 8.3 八类候选能力的目标位置

| 候选 | V4.2 决策 | 运行角色 |
| --- | --- | --- |
| Anthropic `frontend-design` | 合并进 `junwei-frontend-design`，不保留重复入口 | Overlay |
| Superpowers | 固定完整 SHA 的外部依赖；先 Repo Pilot | Standard/Governed 实现 Driver |
| OpenSpec | Governed 规格 Pilot；与 `spec-kit-xl` A/B | 规格 transition Driver |
| Find Skills | 仅用于候选发现，不自动安装 | 治理面工具 |
| AnySearch | 公开非敏感检索的显式 Lab Pilot；结论回到一手来源 | 治理面可选 provider |
| Remotion | 出现真实视频项目缺口后 repo-local Pilot | Media Overlay |
| Skill Creator | 吸收创建、触发和 Eval 方法 | 治理面 Skill 工厂 |
| SkillFather | 仅借鉴生命周期、模板和评测方法，不作为默认依赖 | 治理面参考 |

Find Skills、AnySearch、Skill Creator 和 SkillFather 不占用默认运行 Skill 列表。Remotion 只在对应项目依赖存在且兼容版本被锁定时加载。

## 9. Eval Harness

### 9.1 评测层级

| 层级 | 目标 | 主要证据 |
| --- | --- | --- |
| L0 Static | 格式、标准、License、secret、lock、链接和 schema | 确定性脚本 |
| L1 Trigger | 应触发、近似误触发、不应触发和未触发 | 实际运行日志 |
| L2 Behavior | 候选是否改善真实任务结果 | with/without 或 old/new 配对任务 |
| L3 Integration | Router、Contract、handoff、Driver、Verifier 是否连通 | 黑盒端到端案例 |
| L4 Safety | 权限、注入、外部副作用和 kill switch | 负向案例与隔离演练 |
| L5 Release | 干净环境安装、manifest、checksum、回滚 | 可复现发布演练 |

### 9.2 Trigger Eval

- 建立 30-50 个独立 Prompt，覆盖目标表达、随意表达、路径上下文、拼写变化和困难近似项。
- 约 40% 作为 held-out 集；描述优化期间不根据其逐项结果调参。
- 每个 Prompt 可重复运行 3 次测稳定性，但统计样本仍按独立 Prompt 计算。
- 记录是否真实调用 Skill，不能只检查最终文本包含了某个 Skill 名称。
- 同时计算 precision、recall、false-positive rate、miss rate 和 run-to-run variance。

初始 SLO：

- Stable 隐式 Skill held-out precision `>= 90%`。
- held-out recall `>= 85%`。
- false-positive rate `<= 5%`。
- 关键近似负例误触发为 `0`。

这些数字是首轮工程门槛，不是行业标准；取得基线后允许通过记录明确调整，但不得为单一候选临时放宽。

### 9.3 Behavior Eval

- 首轮选择 5 个不同任务家族的真实配对任务。
- 使用 clean HOME、独立 worktree、相同代码快照、模型、权限、工具、超时和依赖缓存条件。
- old/new 或 without/with 的运行顺序随机交换。
- 人工评审尽量不知道候选版本；机械条件使用确定性断言。
- 结果不明确时扩展到 10-20 个任务，不用重复同一任务伪造独立样本。
- 记录任务成功、人工纠偏、返工、遗漏验证、token、耗时和工具调用量。

初始晋升信号：

- 主要任务成功率提升至少 10 个百分点；或
- 成功率不劣于基线超过 3 个百分点，同时中位 token 或耗时降低至少 20%；并且
- 人工纠偏和返工不高于基线；并且
- 未授权安装、外部写入、密钥暴露、提示注入成功和审批伪造均为 0。

全局 Stable 必须覆盖多个任务家族和多个代表性仓库。不得用固定调用次数替代任务多样性，也不得只用模型自评作为晋升证据。

### 9.4 Eval 产物

每次正式评测生成：

- harness、模型、Codex 和依赖版本。
- 代码与 catalog/lock commit。
- Prompt 集版本与 held-out 标识。
- 每次运行的隔离环境和权限摘要。
- 原始机器断言、盲评结果和人工裁决。
- token、耗时、工具调用和失败分类。
- promote、hold、tighten、rollback 或 retire 结论。

原始 transcript、凭据和敏感项目数据不进入公开 Git；仓库只保存脱敏报告与可复现元数据。

## 10. Profile 与分发目标

插件不是 V4.2 的起点，而是 Stable 能力验证后的分发结果。目标 Profile 为：

| Profile | 内容 | 默认状态 |
| --- | --- | --- |
| `junwei-core` | 薄路由、onboarding、研究、安全/依赖 guardrail、决策、发布检查 | 唯一默认候选 |
| `junwei-design` | 合并后的 frontend design、frontend QA、按需浏览器工具 | 前端项目按需 |
| `junwei-media` | product demo 与经过验证的 Remotion overlay | 项目按需 |
| `junwei-reverse` | 轻量显式 router；重型工具独立获取 | 不默认安装 |

`junwei-lab` 不作为运行插件。Lab 是 Eval 开发工作区，与默认 Skill 发现路径物理隔离。

最终插件边界必须由 P1-P4 的证据确认；如果单个 repo-local Skill 已满足需求，不为“结构完整”强制创建插件。

## 11. P0-P6 实施计划

每个阶段都以退出门禁为完成条件，不按日期或代码量宣布完成。共享入口、schema、安装器和发布脚本由单一 owner 串行集成；独立审计、测试案例和文档可并行。

### P0：可信基础修复

目标：在引入任何外部 Skill 前，消除已知安全冲突和不可复现依赖。

实施项：

1. 删除全局逆向规则中的预先授权、强制副作用和拒绝安全边界的表述，统一回到最小权限和明确批准。
2. 将 reverse router 改为显式启用；默认安装不再复制 reverse pack 或 bootstrap 工具。
3. 盘点并锁定 `@latest`、`HEAD` clone、Docker `:latest`、浮动 GitHub Action 和其他移动依赖。
4. 增加根 License、第三方 notices、依赖清单和基础 SBOM 生成/核验。
5. 建立最小 CI：静态验证、单元测试、manifest、secret/license 检查和干净构建。
6. 修复源码、`VERSION`、manifest、归档和发布说明的漂移。
7. 停止把新 tarball 提交到 Git；准备 GitHub Release asset 路径。
8. 为安装器增加 Profile/可选包语义、dry-run 和卸载/回滚前置设计。

退出门禁：

- 全局规则中不存在预先批准或强制实际副作用。
- 默认 dry-run 不包含 reverse pack、重量级工具或外部服务。
- Stable 依赖不存在浮动引用。
- CI 在干净 checkout 通过。
- 当前源码可以生成带 checksum、manifest 和 License 信息的可复现候选包。

### P1：建立真实基线与治理骨架

目标：先测量现有 14 个 Skill，再决定合并或新增。

实施项：

1. 创建 `catalog/components.yaml` 和 schema。
2. 创建 Resolver 与 `catalog/upstreams.lock.json`，禁止人工直接编辑 lock。
3. 清点 14 个 Skill 的角色：Driver、Overlay、Guardrail、Verifier 或治理工具。
4. 将非标准顶层 frontmatter 字段迁移到 catalog 或标准 `metadata`。
5. 记录描述预算、触发重叠、隐式状态、写入面、网络面和 License。
6. 为现有路由建立 30-50 个独立 Prompt 基线集。
7. 用真实 Codex 日志记录触发，不再把手写关键词 oracle 当作功能证明。
8. 为 debug-loop、completion-review、spec-kit-xl、frontend-qa 等可能重叠能力建立待比较假设。

退出门禁：

- 100% packaged components 在 catalog 有 owner、角色、状态、权限和 License。
- 100% 外部组件有精确 SHA 与内容哈希，或被明确隔离为 Discovered/Hold。
- 现有 14 个 Skill 的 baseline 触发报告可复现。
- 没有候选因为“已经在仓库中”被自动视为 Stable。

### P2：薄核心、Router、Contract 与状态机

目标：建立新的运行模型，但先保持兼容和可观测。

实施项：

1. 精简 `global/AGENTS.md`，把按需细节迁移到 Skill、reference 或 repo docs。
2. 实现 Fast/Standard/Governed Policy Router 和单调升级规则。
3. 定义 Task Contract schema、最小权限默认值和分级持久化规则。
4. 定义 task transition table 与 skill lifecycle transition table。
5. 为策略字段标记 `enforced/verified/advisory/unavailable`。
6. 实现 Contract validator，拒绝非法 transition、双 Driver、伪造批准和权限缺失。
7. 明确 Overlay、Guardrail、Verifier 的输入输出契约。
8. 保留 V3.2 兼容路由作为观测基线，不在一个变更中同时替换所有行为。

退出门禁：

- Router 对安全/外部副作用案例的 Governed 漏判为 0。
- 同一 transition 无法声明两个 Driver。
- Governed 的关键 unavailable enforcement 会 fail closed。
- Fast 任务不会生成持久化 Contract。
- `AGENTS.md` 精简至少 50%，且安全、验证和用户稳定偏好回归测试通过。

### P3：黑盒 Eval、Shadow、Canary 与回滚

目标：把“Skill 有价值”从文档断言变成运行证据。

实施项：

1. 构建 clean HOME/worktree 的黑盒 Eval Harness；明确干净目录本身不是操作系统沙箱。
2. 实现 trigger、behavior、integration、safety 和 release 五类套件。
3. 实现 Shadow：只给路由建议，无工具、无写入、无执行控制权。
4. 实现 Repo Canary：仅对显式项目/任务家族启用固定候选。
5. 实现 kill switch、last-known-good 和一键/单步回滚路径。
6. 建立随机顺序配对、盲评、确定性断言与人工裁决格式。
7. 将现有静态 verifier 降级为 L0/L3 的一部分，不再单独宣称真实行为通过。
8. 对证据保留、脱敏和仓库外 transcript 制定规则。

退出门禁：

- Harness 能在隔离环境重复得到同类结果并记录版本；任何非 fixture adapter 在执行前必须通过宿主提供的可信 `isolation_verifier`。
- Shadow 无法写文件、调用外部工具或改变实际 Driver。
- Canary 可在严重失败后回到 last-known-good。
- 安全负例和伪审批测试通过。
- Eval report 能被 release gate 机器读取。

### P4：单变量候选试验

目标：按顺序验证最可能带来收益的能力，每次只改变一个主要变量。

顺序：

1. 将 Anthropic frontend-design 方法合并进 `junwei-frontend-design`，消除重复触发与职责重叠。
2. 以固定 SHA 引入 Superpowers Repo Pilot，验证 Standard/Governed 实现 Driver。
3. 以显式 Pilot 比较 OpenSpec 与 `spec-kit-xl` 的规格 transition。

每个候选执行：

```text
Audited
  -> Shadow
  -> Repo Pilot
  -> 5 个配对真实任务
  -> 结果明确则 promote/hold/retire
  -> 结果不明确才扩大到 10-20 个任务
```

退出门禁：

- 每次试验只改变一个主要组件或描述集合。
- frontend 合并后触发和行为不低于基线，且默认入口减少。
- Superpowers 的收益超过额外流程与上下文成本。
- OpenSpec 与 `spec-kit-xl` 不长期并存为同一 transition 的 Stable Driver。
- 所有结论有 paired report 和人工裁决。

### P5：淘汰重复能力并插件化 Stable 结果

目标：先减少重叠，再分发已经证明有效的能力。

实施项：

1. 根据 P1-P4 数据合并、收窄或退役重复 Skill。
2. 评估 debug-loop、completion-review 是否被 Superpowers/Verifier Policy 覆盖。
3. 评估 frontend-qa 是否作为 design Profile 的 Guardrail 保留，而不是独立宽触发入口。
4. 只为跨仓库 Stable 组合建立 Codex plugin 和个人 marketplace entry。
5. 将 reverse 拆为显式插件/独立可选包，重型工具不进入 core release。
6. 为每个 Profile 提供安装、dry-run、disable、uninstall 和 rollback。
7. 验证默认隐式描述预算、触发混淆和项目 Skill 余量。

退出门禁：

- 每个默认 Skill 有不可替代的明确职责和 Eval 证据。
- 默认运行环境不包含 Lab、Pilot 或 reverse 重型能力。
- 所有 Stable 插件可独立安装、禁用、卸载和回滚。
- plugin manifest、marketplace、catalog、lock 和 release manifest 一致。

### P6：可复现发布与持续治理

目标：将胜出能力发布为可重现、可回滚的 V4.2，并建立后续更新纪律。

实施项：

1. 从干净 commit 构建 release，不从开发工作区收集文件。
2. 生成 release manifest、archive checksum、SBOM、third-party notices 和 Eval 索引。
3. 在隔离 HOME 做安装、重复安装、冲突、卸载和回滚演练。
4. 通过 GitHub Release 发布不可变资产；仓库不新增 release tarball。
5. 将候选更新流程固定为 staging -> eval -> human diff review -> lock update -> release。
6. 定期检查上游安全、License、兼容性和触发漂移。
7. 只有出现被真实任务证明的缺口时，才依次评估 Remotion、AnySearch 或其他领域能力。

退出门禁：

- clean checkout 可重现相同 release manifest 和内容 hash。
- 新机器演练不依赖开发机缓存或未声明全局状态。
- 回滚到 last-known-good 已真实演练。
- release asset、manifest、tag、源码 commit 和 Eval report 可相互追踪。
- 默认 Profile 的安全违规为 0，触发与行为指标达到已声明 SLO。

## 12. 并行实施边界

在不共享写入文件时，可以并行：

- 仓库/Skill inventory 与 License 审计。
- Trigger Prompt 设计与安全负例设计。
- reverse 供应链盘点与 release 流程审计。
- frontend、Superpowers、OpenSpec 候选的只读研究。
- 独立 reviewer 对计划、schema 和测试覆盖做只读审查。

必须由单一 owner 串行集成：

- `global/AGENTS.md`。
- catalog/lock schema 和 Resolver。
- Task Contract 与 transition schema。
- `install.sh` / `install.ps1`。
- `verify_toolkit.py` 和 release gate。
- 同一个 Skill 或同一个 Profile manifest。

主 agent 负责共享边界、最终 diff、集成验证和 release 决策；Subagent 的完成状态不能直接等同于阶段完成。

## 13. 关键验收指标

### 13.1 安全与供应链

- 未授权外部写入：0。
- 凭据泄露或记录明文凭据：0。
- 模型伪造审批后继续执行：0。
- Stable 浮动依赖：0。
- 默认 reverse/bootstrap/外部服务启动：0。
- 每个 Stable 外部组件具备完整 SHA、内容 hash、License 和 last-known-good：100%。

### 13.2 运行复杂度

- 全局 `AGENTS.md` 初始减少至少 50%，且核心安全回归测试不退化。
- 默认 Skill 描述预算不超过检测到的平台预算 50%。
- 默认入口数以 6-8 个为观察起点，不作为脱离触发数据的硬门槛。
- Fast 任务持久化 Contract 数：0。
- 同一 transition 多 Driver：0。

### 13.3 Skill 质量

- held-out precision `>= 90%`。
- held-out recall `>= 85%`。
- false-positive rate `<= 5%`。
- 关键近似负例误触发：0。
- 行为任务成功率、纠偏和返工达到第 9 节晋升信号。

### 13.4 发布与恢复

- clean build 可复现。
- manifest/lock/catalog/release asset 可追踪一致。
- kill switch 覆盖 Stable 组件：100%。
- last-known-good 回滚演练通过：100%。
- Lab/Pilot 进入默认安装路径：0。

## 14. 回滚与退役规则

立即回滚条件：

- 发生未授权外部写入、凭据暴露、审批绕过或破坏性副作用。
- 候选导致关键安全边界漏判。
- 安装/升级无法恢复到 last-known-good。
- 组件来源或 License 失去可验证性。

常规退役条件：

- 连续评测显示不改善结果或只增加 token/耗时。
- 与另一个 Stable 组件职责重叠，且无独立收益。
- 上游停止维护、兼容性长期失败或安全修复不可用。
- 触发长期过宽/过窄且无法通过描述与边界修正。
- 真实任务缺口已消失。

退役流程：

```text
Stable
  -> Deprecated（关闭隐式调用、声明替代项）
  -> 迁移与回归验证
  -> Retired（移出运行路径，保留 lock/Eval/release 记录）
```

## 15. 明确不做

V4.2 不做以下事项：

- 不一次性安装或复制 frontend-design、Superpowers、OpenSpec、Find Skills、AnySearch、Remotion、Skill Creator 和 SkillFather。
- 不以 Skill 数量、星标或主观评分作为成功指标。
- 不创建新的通用 orchestrator、planner、dispatcher、queue、swarm 或后台 runtime。
- 不恢复与 Superpowers 重叠的 `implementation-plan` Skill。
- 不让 OpenSpec 和 Superpowers 同时控制实现。
- 不要求 Fast 任务写 Task Contract 文件。
- 不把 Task Contract 当作沙箱或权限授予机制。
- 不从任务文本、历史规则或模型推断生产/外部写入已获批准。
- 不默认启用 reverse、MCP server、hooks、memory writer、code graph daemon、watcher 或外部 SaaS。
- 不允许 Find Skills 自动全局安装候选。
- 不允许 AnySearch 或其他聚合搜索替代一手来源核验。
- 不让实现者的自评成为唯一 Verifier。
- 不把重复运行同一 Prompt 计作多个独立样本。
- 不为达到固定调用次数而刷取 Stable 证据。
- 不在 V4.2 常规迁移中重写 Git 历史；历史清理需要独立批准、备份和迁移方案。
- 不复制 License 不明或不兼容的外部内容进入 portable release。

## 16. 风险登记

| 风险 | 表现 | 缓解 |
| --- | --- | --- |
| 流程税反弹 | 小任务也生成 Contract、计划和报告 | Fast 内存状态；以通道和证据决定仪式 |
| 伪 enforcement | YAML 看似严格，工具仍可越界 | 标记 enforcement 等级；Governed 关键缺口 fail closed |
| Driver 竞争 | OpenSpec、Superpowers、自定义 Skill 同时推进 | transition schema 唯一约束与集成测试 |
| Eval 过拟合 | 根据 held-out 逐项调描述 | 冻结 held-out；多任务家族；新 Prompt 扩展 |
| Eval 成本过高 | 所有任务都三次运行和新上下文复核 | 仅候选评测重复；运行时确定性优先 |
| 上游漂移 | tag 移动、依赖更新、兼容失效 | exact SHA、内容 hash、lock、staging update |
| Lab 泄漏 | Pilot 被默认安装或隐式调用 | 物理隔离、manifest 测试、kill switch |
| 证据泄密 | transcript 含私有代码或凭据 | 脱敏摘要入 Git；原始数据隔离与保留策略 |
| 仓库继续膨胀 | tarball 和重型工具持续提交 | GitHub Release assets；reverse 独立包 |

## 17. V4.2 完成定义

只有同时满足以下条件，才可以宣布 V4.2 完成：

1. P0-P6 的退出门禁全部有机器证据或明确人工签署。
2. 安全授权冲突、移动依赖和 reverse 默认安装已消除。
3. catalog、lock、Eval report 和 release manifest 职责独立且可相互追踪。
4. Fast/Standard/Governed Router 与 Task Contract 已通过黑盒案例。
5. Contract 和 Enforcement 的能力差距被显式记录，Governed 不依赖伪强制。
6. OpenSpec/spec-kit 与 Superpowers 的 transition 交接不存在双 Driver。
7. Stable Skill 通过 held-out trigger、paired behavior、安全和回滚评测。
8. Lab/Pilot 不进入默认运行环境。
9. 默认能力数量和描述预算比 V3.2 收敛，且真实任务人工纠偏/返工不增加。
10. clean checkout 能构建、安装、验证、卸载并回滚发布产物。

在这些证据完成前，可以使用“V4.2 implementation candidate / evidence pending”，但不能使用“V4.2 release complete”或“V4.2 proven optimal”。

### 19.2 有意保持 Hold 的实证工作

以下项目不是代码缺失，而是必须使用真实任务、真实 runner 或外部签署才能产生的证据；不得在本仓库中伪造：

1. 冻结的 40-Prompt 路由基线和当前 14-Skill Profile 的 5-case 行为 pilot 已完成并保留原始证据；前者通过路由指标但增加开销，后者无成功率收益且结论为 `tighten`。二者都不是最终 clean commit 的 promotion report，也未取得 owner/独立 reviewer attestation。
2. 对 Anthropic `frontend-design` 合并结果、Superpowers、OpenSpec 与 `spec-kit-xl` 仍须依次做单变量 Shadow 和候选级 paired behavior eval；当前“14 Skills 对空 Profile”的 pilot 不能回答哪个 Skill 应晋升或退役。首轮 5 个不同任务家族，结果不明确时才扩到 10-20 个。
3. 在上述证据出现前，不淘汰 `debug-loop`、`completion-review`、`frontend-qa` 或 `spec-kit-xl`，也不把任何外部候选写成 Stable。
4. Find Skills 仅发现候选；AnySearch 仅可作为显式 Lab；Remotion 只在真实视频项目出现依赖缺口时评估；Skill Creator 和 SkillFather 只吸收方法，不进入默认发现面。
5. 从最终 clean commit 构建正式候选，并从该 archive 重跑安装、重复安装、冲突、prune、卸载和 rollback 的发布签署演练已完成；剩余的是正式 owner/reviewer 签署，而不是本机发布机制缺失。
